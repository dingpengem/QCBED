# AGENTS.md

## Project goal

Rewrite the legacy Fortran multislice QCBED program as a Python package.

The current target is a CPU implementation using NumPy and SciPy.
Independent incident tilts will be parallelized using Python processes.
GPU acceleration may be added later, but GPU dependencies must not be
introduced during the current stage.

## Repository layout

- `private predecessor sources`: original Fortran source; treat it as read-only.
- `reference_data/`: inputs and outputs generated by the Fortran code.
- `src/qcbed/`: new Python implementation.
- `tests/`: numerical and functional tests.
- `benchmarks/`: performance and scaling benchmarks.
- `docs/`: architecture and numerical-convention documentation.

## Critical scientific requirements

- Preserve the physics and numerical conventions of the Fortran program.
- Do not silently change equations, units, coordinate systems, FFT signs,
  normalization, array orientation, or boundary conditions.
- Distinguish clearly between x/y coordinates and row/column indices.
- Record whether angles are expressed in degrees, radians or milliradians.
- Record whether lengths are expressed in angstrom, nanometer or meter.
- Initially use complex128 unless a test explicitly evaluates complex64.
- The legacy Fortran output is the numerical reference.
- Every translated numerical routine must have an equivalence test.
- Compare intermediate complex wavefunctions, not only final intensities.
- Do not copy legacy fixed array capacities into the Python design.
- Allocate Python arrays dynamically from parsed input dimensions.
- Do not treat a private predecessor implementation-only declaration as authoritative unless
  corroborated by current source or reference data. The current private predecessor implementation
  is a user-supplied related-version declaration reference; see
  `docs/source_provenance.md`.
- Do not claim numerical equivalence without executable comparison.

## Development workflow

1. Analyze the relevant Fortran routines before translating them.
2. Document inputs, outputs, array shapes, units and call relationships.
3. Implement and validate a serial NumPy/SciPy version.
4. Add CPU tilt parallelism only after the serial version is validated.
5. Profile before optimizing.
6. Keep translation, parallelization and numerical optimization as
   separate changes.

## CPU parallelization

- Parallelize independent incident tilts.
- Do not parallelize sequential slice propagation.
- Prefer `ProcessPoolExecutor` over Python threads.
- Limit FFT/BLAS libraries to one thread inside each worker.
- Avoid repeatedly serializing large read-only arrays.
- Preserve deterministic output ordering.
- Serial and parallel outputs must agree within the documented tolerance.

## Future GPU compatibility

- Keep physics kernels separate from scheduling and I/O.
- Isolate FFT operations behind a small backend interface.
- Do not add CuPy, JAX or other GPU dependencies yet.
- Avoid design choices that require rewriting the physics code for a
  future GPU backend.

## Editing restrictions

- Do not modify files under `private predecessor sources` unless explicitly requested.
- Do not delete or replace reference data.
- Do not make unrelated code changes.
- Do not claim numerical equivalence without running the relevant tests.

## Completion requirements

After changing numerical code:

- Run the relevant unit tests.
- Run Fortran-reference equivalence tests if reference data are available.
- Report numerical errors and test results.
- Report benchmark results only when measured.
